# AI From Zero v4.3 content audit

Produced per the v4.3 spec's Section 31, Step 2. This is a read-only inspection
report: the repository was not modified to produce it. No code, data or content
file changes are included in this document or in the commit that adds it.

## Scope and source

The source document is *AI From Zero — Applied AI PM/Engineer-Focused Track,
v4.3 Claude Code Spec* (5,747 lines), supplied as an upload rather than a
checked-in file. It was read in full — Sections 1–32 (the implementation
specification: tiers, data model, artifact/mastery/progress schemas,
migration strategy, developer execution plan, definition of done) and
Section 33 onward (the canonical curriculum text: the v3.1 foundation,
Chapters 8–21, and Appendices A–F including Chapters A1–A8 and B1–B8).

This audit inspects the repository as it stands on branch
`claude/clear-repo-rules-files-rkofxs` and compares it against that spec. It
does **not** propose or make any schema, content or code changes — those are
Steps 3–12 of the spec's developer execution plan, which are explicitly out
of scope until this audit has been reviewed.

## A discrepancy worth flagging immediately

The spec's Step 1 instructs inspecting a file named `aifz-chapters.json`. No
such file exists anywhere in this repository, and nothing in the build or
runtime pipeline produces or consumes one. The actual content pipeline is:

```
src/data/*.js  →  build.js  →  content/defaults.json  (+ dist/index.html,
                                dist/artifact.html, dist/site/)
```

Chapters, skills, items, exercises, processes, reference data and the
Hinglish translation layer are hand-authored JS modules under `src/data/`,
concatenated by `build.js` into a single inline `<script>`, and also emitted
as `content/defaults.json` for the database-backed deployment to seed from.
Everything in this audit refers to that real pipeline, not to the spec's
assumed file.

## Existing portal structure (as inspected)

- **Build.** `build.js` reads an ordered list of `src/data/*.js` files (base
  content first, then the Hinglish layer, keyed on exact English strings),
  concatenates them into `dist/artifact.html`, `dist/index.html` and
  `dist/site/`. `npm test` runs `build.js` → `tools/content-check.mjs` →
  `tools/style-check.mjs` → `tools/v31-content-check.mjs` → `tools/test.mjs`.
- **Runtime content source.** `src/content.js` defines `window.CONTENT`,
  which loads chapters/skills/items/exercises/processes/reference/hinglish
  from a Postgres/PGlite-backed API (`api/content.js`, `kind` ∈ `chapters,
  items, skills, exercises, processes, reference, hinglish`) when available,
  falls back to a `localStorage` cache, and finally falls back to the
  bundled built-ins. The database's `kind` enum is fixed; there is no spare
  content kind for a new artifact-vault/decision-log/failure-log dataset
  without either adding a new `kind` or nesting it inside `reference`.
- **Learner progress.** `api/state.js` stores one JSON blob per user in a
  `progress` table (`data jsonb`), versioned with optimistic-concurrency
  conflict detection and a 20-entry history. This is schema-free on the
  server: new keys in the client-side state object need no migration there.
- **Chapter schema.** Each chapter object carries `id, num, part, minutes,
  labs[], title, concept, takeaway[], story[]`, and optionally `plan{first,
  build,brk,artifact,gate}`, `needs[]` (prose prerequisite explanations, not
  a chapter-id graph), `words[]` (glossary pairs), `check[]` (question/answer
  pairs), and `capstone{title,brief,steps[],done[]}`. There is no `tier`,
  `priority`, `phase`, `prerequisites[]`, `nextUnits[]` or `mastery{}` field
  anywhere on a chapter.
- **Block grammar (`story[]`).** `p, h, key, c, l, n, tb, code, x, do, q,
  pred, try, snag, lab, unit`. Documented at the top of `src/data/part1.js`.
- **The `unit` block already matches v4.3's per-subsection structure.** A
  `unit` block is `['unit', '8.1', 'Title', {goal, idea, prove, build, brk,
  artifact, check, lens}]`. Comparing this directly against the spec's
  Chapter 8–21 source text (IDEA / PROVE IT / BUILD / BREAK / ARTIFACT /
  CHECK YOURSELF / APPLIED AI PM·ENGINEER LENS, per numbered subsection) —
  the field names differ (`idea/prove/build/brk/artifact/check/lens`) but
  the content is a near-verbatim, subsection-numbered match. There are
  **90 `unit` blocks**, all in `src/data/part5.js` (Chapters 8f–21cap, i.e.
  the spec's Chapters 8–21). The only spec field with no home on the `unit`
  object is per-subsection `BRIDGE` text (the repo's `plan.gate`/chapter
  intro carries an equivalent chapter-level "why next" instead). Track A and
  Track B chapters (`a1`–`a8`, `b1`–`b8`) use a looser `Idea N` heading +
  `do`/`tb` pattern, not the strict `unit` grammar — 0 `unit` blocks there.
- **Mastery/competency tracking that already exists.** `src/engine.js`
  implements a 30-skill (`S01`–`S30`) mastery-with-decay + SM-2 spaced-
  repetition model, driven by quiz items (`ALL_ITEMS`), independent of
  chapters. Separately, `S.arts` (Appendix B's 22-row artifact tracker)
  holds `{s: 0|1|2, where}` per artifact — a **3-state** scale (not
  started/in progress/done), not the spec's 0–3 four-state "absent /
  attempted / usable / decision-grade" scale. That exact four-state rubric
  is already **printed as prose** at the end of every B-chapter ("Mastery
  gate. Score 0 = absent, 1 = attempted, 2 = usable, 3 = decision-grade…")
  but is not backed by any stored state — it is copy, not data. `S.tpl`
  tracks which of the nine Appendix C templates have been filled. `S.done`,
  `S.cp` and `S.att` track chapter completion, free-text checkpoint answers
  and quiz attempts respectively. There is no unified `Progress` object with
  the spec's five booleans (`read/proved/built/measured/defended`) plus a
  `masteryScore`.
- **Existing name collision risk.** A field literally named `tier` already
  exists — on **exercises**, not chapters (`src/data/work.js`,
  `src/data/exercises5.js`, and the editor stub in `src/studio.js`), an
  integer 1–4 meaning exercise difficulty. Reusing `tier` for the spec's
  `core|selective|reference|parking-lot` chapter classification would
  collide in name with an unrelated, already-shipped field of a different
  type and meaning.
- **Validation.** `tools/content-check.mjs` (schema/ID/terminology/parity
  checks), `tools/style-check.mjs` (coding-book voice per
  `CONTENT-GUIDELINES.md` §8), `tools/v31-content-check.mjs` (regression
  guard for specific v3.1 phrasings), `tools/jargon-check.mjs`. None of them
  currently know about tier/mastery/artifact-vault concepts, so any of
  those additions needs matching validator work, not just data changes.

## Missing units

Nothing in the spec's *curriculum content* (Chapters 1–21, A1–A8, B1–B8,
Appendices A–F) is absent from the portal — every chapter and every
numbered subsection has a corresponding, near-verbatim home. What is
missing is entirely on the **data-model / feature side** (spec Sections
6–17, 23–29):

1. **No tiering metadata.** No `tier` (`core|selective|reference|
   parking-lot`), `priority`, or `phase` field on any chapter or unit.
   Depth guidance ("TRACK DEPTH: SELECTIVE · ~4 hours") exists only as text
   in the spec, not as portal data or UI (no "Role-fit note" pattern).
2. **No typed `sections[]`.** The `unit` object's eight fixed sub-fields
   cover the spec's `idea|prove|build|break|artifact|check|pm-lens` content,
   but as fixed keys on one object, not as an ordered, independently
   addressable `sections[]` array. There is no `bridge` section type stored
   per unit.
3. **No typed `artifacts[]` with `required: boolean`.** Each `unit` has one
   free-text `artifact` string. `APPENDIX.artifacts` is a flat 22-row list.
   Neither carries a `type` enum (`experiment|engineering|decision|
   evidence`) or a `required` flag per unit, though the nine
   `APPENDIX.templates` are already typed by `key` (`exp, fail, adr, prd,
   risk, vendor, evalcase, trace, gate`), which is the closest existing
   analog to an artifact-class taxonomy.
4. **No `mastery: {questions[], passingScore}` block.** `check[]`
   question/answer arrays exist per chapter; there is no bound quiz set or
   numeric passing threshold used for mastery gating.
5. **No `prerequisites[]` / `nextUnits[]` graph.** `needs[]` exists but is
   prose (title, one-sentence reason, and a loose chapter link), not a
   machine-usable dependency array suitable for unlock logic.
6. **No unified `Progress` type.** No stored `read/proved/built/measured/
   defended` booleans or 0–3 `masteryScore` per unit. The closest existing
   state is `S.arts[n] = {s: 0|1|2, where}` (per named artifact, 3-state)
   and `S.tpl`, `S.done`, `S.cp` (binary/free-text, not per-unit mastery).
7. **No first-class Artifact Vault.** `S.arts` records a status and a
   free-text "where," not the artifact's actual content, link or file.
   There is no page that shows "everything you have produced" as a vault.
8. **No first-class Decision Log or Failure Log**, distinct from the
   generic ADR/Failure-Finding templates already in the Workbench. Today a
   learner fills those templates ad hoc; nothing aggregates "your decisions"
   or "your failures" as its own running, chapter-linked feed.
9. **No "Defend This Decision" exercise pattern** implemented as a distinct,
   reusable interactive block type. The closest existing analogs are the ADR
   template's "what would reopen this" field and B8's Gate 5 "defend" prose
   — neither is a structured, repeatable exercise pattern.
10. **No "Technical Interview Lens" block**, separate from the existing
    per-unit `lens` field (which already renders the spec's "APPLIED AI PM /
    ENGINEER LENS" line) and from B7's interview-prep content.
11. **No merged, 11-stage capstone** (Discover→Define→Design→Build→
    Evaluate→Break→Observe→Ship→Measure→Iterate→Defend) with 21 required
    evidence items as one structure — see "duplicate units" immediately
    below, since the content that would feed it currently lives in two
    places.

## Duplicate units

1. **Two capstones, not one.** `ch21cap` (Part V, 6 `unit` subsections:
   21.1 PRD → 21.2 vertical slice → 21.3 evaluation/observability → 21.4
   break it → 21.5 optimize → 21.6 defend) and `b8` (Track B, a separate
   5-gate structure: Discovery → Strategy → Build → Ship → Defend) are both
   full, standalone capstone chapters today. The spec is explicit that B8
   is "MERGED INTO CHAPTER 21 · do not run as a second capstone" and that
   the merged result should be an 11-stage pipeline with 21 required
   evidence items. The portal currently ships the pre-merge state: two
   separate capstones, 6 stages in one and 5 gates in the other (11 stages
   combined, which is suggestive — a straightforward merge candidate, but
   not yet done). This is the single largest structural gap between the
   portal and the spec.
2. **`b4` ("The applied AI PM toolchain") directly contradicts its own
   spec entry.** The spec's own Appendix ("REFERENCE — Do Not Complete
   These as Full Courses," entry "B4 — Full applied-AI toolchain") calls
   this "the biggest cut" and says explicitly: "Do not learn ChatGPT,
   NotebookLM, Gems, Figma, Lovable, AI Studio, Claude Code, Cursor, n8n,
   Antigravity, GitHub, Jira, Postman, Vercel, Supabase, AWS, PostHog,
   Mixpanel and GA as separate subjects. Pick one tool per job and learn
   the underlying capability." The portal's `b4` is a full 960-minute (16
   hour) required chapter that tours exactly that kind of broad toolchain
   ("Learn the tools an applied AI product manager uses to research,
   prototype, build, deliver and measure… use each group of tools on your
   capstone"). This is not a wording mismatch — it is the one place where
   the portal's existing content is structurally opposite to what the spec
   asks for. The spec wants a toolchain **policy table** ("one tool per
   capability"), not a 16-hour tool tour.
3. **A1–A7 are built as full required courses (360–840 minutes each);
   the spec later marks A1–A7 reference-only** ("REFERENCE — Do Not
   Complete These as Full Courses… skip the beginner PM onboarding… use as
   a reference… do not repeat generic PM training"). This is not a content
   duplicate in the strict sense — the topics are not taught twice — but
   it is a depth mismatch worth carrying into the same bucket as the above,
   since resolving it (build vs. reference-only) is the same kind of
   tiering decision as the B-track case above.

## Migration risks

1. **No spare content `kind`.** The backend's content table has a fixed
   `kind` enum (`chapters, items, skills, exercises, processes, reference,
   hinglish`). Any new server-editable dataset (a tiering table, a mastery
   question bank distinct from `check[]`) needs either a new `kind` value
   (API + Content Studio changes) or must be folded into the existing
   `reference` kind, which already carries a large, growing `APPENDIX`
   object.
2. **`tier` name collision.** A chapter-level `tier` (core/selective/
   reference/parking-lot) would collide in name, type and meaning with the
   existing exercise-level `tier` (integer 1–4, difficulty) in
   `src/data/work.js`, `src/data/exercises5.js` and `src/studio.js`. A
   different field name (e.g. `depth`) avoids this without any functional
   loss.
3. **Progress-shape change is not backward compatible for in-flight
   learners.** `S.arts` is a 3-state scale keyed by artifact number;
   B-chapters already print a 4-state (0–3) mastery-gate rubric in prose.
   Introducing a real 0–3 `masteryScore` either needs to coexist with
   `S.arts` (two parallel scales for the same thing, confusing) or needs an
   explicit migration function translating existing saved `{s:0|1|2}` rows
   into the new scale for any learner who already has progress saved
   server-side (`api/state.js`'s `progress` table). Silently reinterpreting
   `s` in place would change the meaning of data a real learner already
   wrote.
4. **Merging `ch21cap` + `b8` changes stable ids.** Progress
   (`S.done`, `S.cp`, `S.arts`, quiz `S.att`) is keyed by chapter id and by
   artifact/template number. The spec's own "Existing Content Preservation"
   rule requires retaining unit IDs and not replacing, only adding
   metadata — a literal merge-and-delete of `b8` would strand any learner
   progress already recorded against it. A merge needs to either keep both
   ids alive (one chapter, or one chapter plus a redirect/alias) or provide
   an explicit progress-migration step, not just a content edit.
5. **Validator coverage.** `tools/content-check.mjs`,
   `tools/style-check.mjs` and `tools/v31-content-check.mjs` do not know
   about tier/mastery/artifact-vault/decision-log/failure-log concepts yet.
   Any schema addition needs matching validator updates in the same change,
   or `npm test` will not catch a malformed new field, and the coding-book
   voice guard (`CONTENT-GUIDELINES.md` §8) won't apply to any new
   generated UI copy (e.g. "Role-fit note" text) unless it is added to the
   same content pipeline the checkers already scan.
6. **Hinglish-layer sequencing.** The Hinglish translation layer
   (`src/data/hing-*.js`) is keyed on exact English source strings. Task
   #23 (in progress, paused for this audit) is mid-way through translating
   the coding-book-style rewrite done in task #22. Any v4.3-driven English
   rewording of the same chapters (e.g. adding `bridge` text, restructuring
   `unit` fields, splitting/merging capstone prose) done **before** that
   translation pass finishes would re-break the batches already translated,
   doubling the work. If the v4.3 restructuring goes ahead, it should
   either happen before resuming the Hinglish backlog, or be scoped to
   avoid re-wording chapters whose English text is already fully
   translated. This audit did not re-count the current translated/
   untranslated split; the session's own task tracker has the up-to-date
   figure.
7. **Scope of Steps 3–12 is large.** Full implementation (chapter/unit
   metadata, an evidence-tracking engine, Artifact Vault, Failure Log,
   Decision Log, capstone-workspace merge, dashboard rework, mobile QA,
   regression QA — the spec's own 12-step plan) is a substantial,
   multi-part engineering effort layered on top of an already large
   codebase (`part5.js` alone is 142 KB; `src/app.js` is one large hand
   -rolled view layer with no framework). It is not a single PR; the spec's
   own Definition of Done (19 items) implies incremental, reviewable
   slices — tiering metadata first, then progress-model changes, then new
   views, would be the natural order, but that sequencing decision belongs
   to the user, not to this audit.

## Proposed changes

These are **not authorized by this audit** — they are the audit's read on
what Steps 3–12 would concretely touch, offered so the user can decide
scope and order. No code or content changes have been made.

1. Add a `depth` field (`'core'|'selective'|'reference'|'parking-lot'`) to
   each chapter object — a new name, not `tier`, to avoid the collision in
   (2) above — plus optional `priority`/`phase` where the spec's study map
   already implies one (`APPENDIX.studymap` has this information in prose
   form already and could seed it).
2. Extend the `unit` object with a `bridge` field and, where useful, an
   `artifactType` (`'experiment'|'engineering'|'decision'|'evidence'`) and
   `artifactRequired: boolean`, reusing the existing template `key` taxonomy
   as the type enum rather than inventing a second one.
3. Design one `masteryScore` (0–3) per unit/chapter, decide how it relates
   to the existing `S.arts` 0/1/2 scale (replace with a migration, or keep
   `S.arts` as the artifact-tracker and add mastery as a separate,
   additional axis — recommend the latter, since they answer different
   questions: "is the artifact done" vs. "how well do you understand this").
4. Build the Artifact Vault, Decision Log and Failure Log as three new
   views reading/writing new keys in the existing free-form `progress`
   JSON blob (low backend risk, per the migration-risk note above), each
   pre-populated from the matching Appendix C template so filling one
   template entry also populates the corresponding log.
5. Merge `ch21cap` and `b8` into one capstone. Recommended approach:
   keep `ch21cap`'s id and Part V slot as the canonical capstone, restructure
   its `unit` list from 6 to the spec's 11 stages by absorbing B8's five
   gates in as additional `unit` subsections (21.7–21.11), and turn `b8`
   into a short redirect/pointer chapter (not deleted, so old progress
   still resolves) that sends the learner to `ch21cap`.
6. Rewrite `b4` from a 16-hour, 17-tool tour into the spec's toolchain
   **policy table** (one tool per capability, with the underlying
   capability as the actual learning objective) — this is a content
   rewrite, not a metadata change, and the largest single content edit
   implied by this audit.
7. Reclassify `a1`–`a7` as `depth:'reference'` (once field (1) exists)
   rather than removing them — the spec's own "Existing Content
   Preservation" rule forbids collapsing chapters, and these are cheap to
   keep as opt-in reading with a "Role-fit note" rather than mandatory
   360–840-minute courses.
8. Update `tools/content-check.mjs` and `CONTENT-GUIDELINES.md` in the same
   change as any schema addition, so validation and the style guide do not
   silently fall behind the new fields.

## Next step

This audit is complete. No further action should be taken on Steps 3–12,
the paused Hinglish translation backlog, or the b4/A-track content rewrite
until the user has reviewed this document and decided which proposed
changes (if any) to authorize, and in what order.
